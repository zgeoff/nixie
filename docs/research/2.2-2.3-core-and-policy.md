# Core, runtime and policy

The Claude Agent SDK fits as the runtime for a single turn, and the research recommends that nixie's
core own everything around the turn: approvals, outside actions, owner messages and the decision
record, kept in nixie's own event log and its own tools. A Claude Code mod inside the SDK can
enforce policy on the SDK's built-in tools, but it fails open in 3 ways, so it cannot be the only
gate. For policy, the research recommends 3 deterministic layers: a rule engine, effects that
nixie's tool registry declares, and a taint label for tasks that read untrusted content. Cedar is
the leading rule engine. imp contains a task's network, but a credential grant reaches its host with
any method, path and body. None of these recommendations is a decision; the last section lists the
decisions they feed.

The findings come from 2 research tracks and 4 spikes, as of 7 October 2026:

- the engine notes in [2.2-notes](./2.2-notes/), and the policy and approval notes in
  [2.3-notes](./2.3-notes/)
- the spikes under [spikes](../../spikes/), each with its code, how to run it, and its output; they
  ran against Agent SDK 0.3.292, Claude Code 2.1.292, imp 0.38.1 and Bun 1.4.2

## The SDK turn

The SDK makes the state inside a turn durable. It writes each session to a transcript, and `resume`
restores that session in a new process. A `PreToolUse` hook that returns `defer` ends the process at
a tool call, and a later `resume` asks the hook again for the same call. The
[defer spike](../../spikes/sdk-long-hold/) confirms both through the SDK: the result carries
`stop_reason: tool_deferred` and `deferred_tool_use`, and the resumed process accepts `allow`,
`deny` or another `defer`. A resume needs an input stream that stays open until the first result. An
empty `prompt` starts a second turn, and a stream that closes at once drops the hook callback, so
Claude Code refuses the call.

Two SDK behaviours put a parked task at risk:

- The SDK deletes local transcripts after 30 days by default (`cleanupPeriodDays`). A task parked
  longer than that loses its session unless nixie raises the setting or keeps its own copy.
- A `SessionStore` write that fails 3 times is dropped, and the SDK emits `mirror_error`. A run
  resumed from the store deletes its local copy, so the dropped batch has no copy left. A design
  that uses the store needs to treat each `mirror_error` as a fault on the task.

## The policy mod

A Claude Code mod loads into an SDK `query()` through `options.plugins`. In the
[mod policy spike](../../spikes/sdk-mod-policy/), `tool.call` and `tool.check` fire for Bash and
Read. A `tool.call` hook denies a call, rewrites its arguments, or answers it without running the
tool. A `tool.check` hook denies a call that an `allowedTools` rule allowed, and the SDK stream then
carries a `permission_denied` message that the adapter can record.

A broken mod lets tool calls run. The spike broke the mod 3 ways:

- **The module throws at load.** Every call runs. `init.plugins` lists the mod, `plugin_errors` is
  empty, and only the debug log records `hooks module did not load`.
- **A hook throws.** The call runs. A `.catch` handler on the registration turns the throw into a
  deny.
- **A hook blocks the hooks worker.** After about 6 s, Claude Code unloads the whole mod, `.catch`
  handler included. The call that blocked the worker runs, and later calls run with no policy.

An adapter can detect a missing mod through a command that the mod registers in `session.start`.
Claude Code lists that command in `init.slash_commands` only after the module runs, so the adapter
can stop the session when the command is absent. After an unload, a `commands_changed` message
arrives without the command, 0.2 s before the result of the call that blocked the worker. That one
call is the residual: it runs before the adapter can react. imp's network policy would contain that
call. Under the proposal design below, nixie's own tools ask the policy decision point whether or
not the mod is loaded.

## Owner approvals

A mod can hold a call while the owner decides, but only by working around 2 limits. A hook has 10 s
of its own time, and one `$.http.fetch` aborts at 30 s. In the spike, a hook that repeated 20 s
long-polls held a call for 6 minutes, because time inside `$.http.fetch` does not count against the
10 s budget. No doc states that accounting rule. When the process dies during a hold, the resumed
session reads `Tool call interrupted ... outcome is unknown`, and the call never runs.

An approval that ends the turn survives a restart, and a hold does not. The engine research
therefore recommends running every outside action as one of nixie's own tools, through a
[proposal design](./2.2-notes/engines.md#recommendation):

1. The tool asks the policy decision point.
2. An allowed action runs once, under an ID that nixie creates.
3. An action that needs approval becomes a proposal with that ID, and the tool returns "pending
   approval" to the model.
4. On approval, nixie runs the action as its own step under the same ID, then starts a turn with the
   result.

The model learns the result one turn later, which is the cost of the design. Under that design, a
hold in `tool.call` stays useful for an answer that arrives in under 30 s, such as a tap on a phone
notification while the owner watches. `defer` stays useful for a single question to the owner, such
as `AskUserQuestion`.

`defer` does not handle a batch of parallel tool calls. The hooks docs state that Claude Code
ignores `defer` in a batch, logs a warning and runs the tools. The spike reproduced different
behaviour 3 times: both calls deferred, `deferred_tool_use` held only the last one, the debug log
had no warning, and the first call never got a result. On resume, the model issued the first call
again under a new ID. The proposal design does not depend on either behaviour.

## Owner messages

`streamInput()` delivers an owner message into a live session, and its priority sets when the model
reads it. The [owner input spike](../../spikes/sdk-owner-input/) sent each priority during a 20 s
shell command:

| Priority                            | The model reads the message | The turn                     |
| ----------------------------------- | --------------------------- | ---------------------------- |
| `next`                              | after the command finishes  | goes on                      |
| `later`                             | after the turn ends         | a new turn starts            |
| `now`                               | after the command finishes  | ends there; a new one starts |
| `now` with `origin: {kind:'human'}` | about 4.5 s after the send  | ends; a new one starts       |

With a `human` origin, Claude Code moves the running command to the background and lets it finish.
The SDK docs state that plain `now` interrupts the turn; the spike found that plain `now` waits for
the same tool boundary as `next`. A live session is not durable. The engine research recommends
writing each owner message to nixie's event log first, so that a message that no finished turn
consumed becomes the prompt of the resumed turn.

## Durable execution

The engine research recommends against adopting a durable execution engine. Each engine adds a
second log of record beside nixie's event log, and the policy decision point would have to reconcile
the two. Bun support is thin: only Restate and OpenWorkflow test Bun in their CI, and Inngest
documents a Bun adapter. Code changes break parked tasks in most engines. Temporal and DBOS need
code patches, Restate keeps the old deployment running until its tasks finish, and Inngest runs new
code against old runs. The [engine notes](./2.2-notes/engines.md) hold the full comparison of 11
engines.

The recommended alternative models each long task as an explicit state machine on nixie's own event
log, instead of replayed code. A task moves through states such as `running_turn`,
`waiting_approval`, `waiting_message`, `sleeping` and `done`. A worker leases the task, runs one
step, and writes the result and the next state in one transaction, keyed by `(task_id, step_key)`. A
deploy cannot break a parked task, because no code replays. One turn is one step, and the SDK
session is that step's checkpoint. The engine notes estimate 800 to 1,500 lines plus crash tests for
leases, timers, retries and wake-ups.

The research ranks Restate as the first fallback if that code proves too costly. It runs as one
binary, tests Bun in CI, and suspends a waiting run so that nixie's process can be down. Its server
is under the Business Source License 1.1, which becomes Apache-2.0 four years after each release.
DBOS is the second fallback: an MIT library on Postgres, but a waiting task keeps a process busy,
and its CI covers Node only. OpenWorkflow and Absurd are reference designs to read, not
dependencies.

## Policy layers

No single policy model meets nixie's principles. The
[policy model notes](./2.3-notes/policy-models.md) compare rule languages, typed effects, capability
systems and information-flow control, and recommend 3 layers. Each layer records the ID of the rule
that decided.

1. **Cedar rules.** Cedar is the only rule engine in the survey that runs inside Bun and returns the
   IDs of the deciding rules. A rerun on Bun 1.4.2 with `@cedar-policy/cedar-wasm` 4.13.0 returned
   `allow-owner-send` for an internal send and `forbid-send-external` for an external one, at about
   0.12 ms per decision. Cedar ignores the `@id` annotation through its API, so a Cedar design
   stores rules as a map keyed by rule name. A deny with no deciding rule means that no rule
   matched, which a design can treat as the cue to ask the owner. OPA, CEL and the ReBAC servers
   each miss a requirement; the policy model notes give the reasons.
2. **Effects from nixie's tool registry.** Each tool declares what it does: read, write, send,
   spend, or change an approval or budget. IronClaw makes payments and changes to approvals or
   budgets always ask, and the research recommends the same set. The MCP spec treats tool
   annotations as untrusted, so the effects come from nixie's registry, not from the tool. The
   research recommends keeping the declarations as owner-editable data, except for the always-ask
   set.
3. **A taint label.** Once a task reads untrusted content, its send, write and spend tools close or
   ask. This follows the FIDES labels and Meta's Rule of Two. All reference code is Python, so this
   layer would be a port to TypeScript that nixie maintains.

The taint layer closes the exits at the tool boundary only. Side channels remain: a conditional
call, an exception message, or a link that a channel renders. imp's network policy is the layer
under it.

## Approval records

The [approval notes](./2.3-notes/approvals.md) survey how products and standards store, bind and
replay approvals, and recommend borrowing the strongest pattern from each:

- **Structure.** An approval record follows the `authorization_details` shape of RFC 9396.
- **Binding.** The record holds a hash of the canonical action, as AP2 binds a payment to
  `checkout_hash`.
- **Replay.** An approval is consumed once, in the same transaction that runs the action. An expiry
  alone does not stop replay.
- **Durable grants.** "Always allow" becomes an ordinary rule that the owner can read and edit.
- **Delegation.** A grant to a subagent may only narrow, and the record keeps the chain of actors.
- **Phone approval.** The CIBA pattern, without an identity provider: an opaque ID, a push message
  with the structured details, an expiry, and a check that the answer came from the owner's identity
  on that channel.

Owner friction is the weak point. Claude Code users approve 93 to 97% of permission prompts, so a
prompt that fires often protects little. Products that feel frictionless put a model classifier in
front of the owner, and nixie's first principle rules that out as the decision point. The
deterministic options are containment, which cut prompts by 84% at Anthropic; risk tiers; drafts in
place of sends; and suggested rules that the owner confirms. A suggested rule that only narrows
access applies at once, and one that widens access asks, as Progent does. No shipping product offers
digest approvals, so a digest design has no precedent to borrow.

## The imp credential broker

The [imp broker spike](../../spikes/imp-broker/) ran a mock OAuth server against a throwaway imp:

- **No method or path limits.** imp matches a grant on the host only. The imp sent `DELETE` and
  `PUT` requests to any path on the granted host, with the credential attached.
- **No token refresh.** The broker injects a static value. After the token expired, requests failed
  with `401` until the host stored a new token.
- **The granted host is an exit.** Under the `none` policy every other route failed, but a 1 MiB
  POST body, a query string and a custom header all reached the granted host.
- **A thin audit.** The broker records method, host, path, status and sizes for each credentialed
  request. It records no query, header or body, and no refused request.
- **A token endpoint leaks.** With a grant on the OAuth token endpoint, the broker added the client
  credentials to the imp's request, and the imp received a live access token and refresh token.

The findings constrain any design that uses imp. A grant to a task that reads untrusted content is
an exit for that task's data. A grant on a token endpoint hands the imp a live token, so token
refresh belongs on the host. The broker's log is too thin to serve as nixie's record. A method and
path filter in imp's broker is a small change, and the spike README gives its location in the
source.

## Open questions

- **Where does `query()` run?** The proposal design keeps nixie's tools in the process that calls
  `query()`, next to the policy decision point. The 2.1 plan puts the SDK inside an imp. Either the
  decision point runs inside the sandbox, or the sandboxed SDK reaches it through a grant, which the
  broker spike shows is an exit. A spike that runs `query()` inside an imp with nixie's tools as an
  MCP server on the host settles it.
- **Do nixie's own MCP tools run in-process under Bun?** The spikes tested mods and `streamInput`,
  not in-process MCP tools.
- **How often does the model batch tool calls in nixie's work?** That sets how often `defer` loses a
  call.
- **Can a check for widening rules run in Bun?** Cedar's analysis tools and Progent's SMT check
  decide whether nixie can apply narrowing rule suggestions without a prompt.
- **How does one digest approval bind several actions?** One hash per action on one approval sheet
  is the first candidate.
- **Postgres or SQLite for the event log?** `kysely-postgres-js` is the safer driver on Bun, and
  `kysely-bun-sqlite` 0.4.0 dates from May 2025.

## Decisions this research feeds

Each item is open, with the research recommendation first:

- **The durable layer:** decided in [0001](../decisions/0001-durable-layer.md): nixie's own event
  log, with tasks as state machines.
- **Outside actions and approvals:** decided in [0002](../decisions/0002-approvals.md): proposals
  for every approval, and the mod as a guard that never waits.
- **The rule engine:** decided in [0004](../decisions/0004-rule-engine.md): nixie's own rule format
  with fixed checks, not Cedar.
- **The effect and taint layers:** decided in [0005](../decisions/0005-effects-and-taint.md):
  declared effects, a 3-effect always-ask set, the tool as the boundary, and a 0-prompt target.
- **The approval record:** decided in [0006](../decisions/0006-approval-record.md): bound to one
  action, used once, "always allow" as a rule with no expiry, and digest approvals.
- **Grants for tasks that read untrusted content:** decided in
  [0007](../decisions/0007-grants-and-taint.md): none for an imp that reads untrusted content.
- **Where `query()` runs:** decided in [0003](../decisions/0003-sdk-placement.md): on the host with
  only nixie's tools for assistant work, and inside an imp for coding work.

## Corrections to the 2.1 landscape

- The 2.1 landscape states, from the hooks docs, that Claude Code ignores `defer` in a batch of
  parallel tool calls and logs a warning. The defer spike found that both calls defer, only the last
  is reported, no warning is logged, and the first call is lost until the model issues it again.
- The 2.1 landscape asks the adapter to check that the policy mod loaded. The mod policy spike found
  the check: a command that the mod registers, read from `init.slash_commands` and
  `commands_changed`. One call still runs when a hook blocks the worker.
- The 2.1 landscape states that imp's egress policy can remove every route out, with an exception
  for granted hosts. The broker spike shows that a granted host accepts any method, path and body,
  so any grant is an exit for a task that reads untrusted content.

# Landscape and architecture models

No existing assistant or framework fits nixie's principles as a whole, and none is a usable skeleton. Every hosted product keeps policy in a model or a prompt and keeps the owner's data with the vendor. Every open-source agent ships its security controls as options with insecure defaults. The parts nixie needs exist across the field, each in one or two projects: a session log with a stateless harness, credentials injected at egress, policy enforced outside the model, and memory kept as a versioned repository of markdown. The Claude Agent SDK fits as the runtime behind nixie's adapter and nothing more.

The survey covers 4 hosted products, 6 open-source agents, 3 frameworks, and the published writing on agent architecture, as of 7 October 2026. The condensed evidence for each subject, with sources and unverified claims marked, sits in [2.1-notes](./2.1-notes/).

## Hosted products

All 4 hosted products put policy in a model or a prompt, keep the owner's data with the vendor, and give the owner no override at the level of a rule. Each still carries one or two mechanisms worth copying.

- **OpenAI Dots.** A dot runs on its own cloud computer, delegates work to background tasks, and stops for a fixed set of handoffs such as password changes and money transfers. Its confirmation policy is text in the model's instructions, and its auto-review is a second model ([GPT-6 Astra system card](https://deploymentsafety.openai.com/gpt-6-astra), section 12). The owner cannot read or edit individual memories, only reset the whole dot. An approval in the parent dot does not carry over to a delegated task ([openai/codex#51349](https://github.com/openai/codex/issues/51349)). Two mechanisms are worth copying: a reviewer that sends the decision to the owner when it reaches none, and background research tools that cannot send, write, or browse.
- **xAI Grok Bot.** Every bot on an account shares one cloud computer, with the same files, cookies, and credentials, and xAI's docs say "Do not use separate Bots as a security boundary" ([FAQ](https://docs.x.ai/grok-bot/faq)). Its automatic approvals are model-based. Worth copying: a message from the owner takes priority over background work and can redirect a running turn, secret fields stay out of the model's context, and an "ask first" rule beats an "allow automatically" rule when both match.
- **Google Gemini Spark.** Google announced Spark on 19 May 2026. Each task shows its done, current, and planned steps, and its hard limits of 15 running tasks and 50 schedules skip a run rather than queue it ([help](https://support.google.com/gemini/answer/17094710)). Google does not document where enforcement sits or keep approval records.
- **Anthropic.** The Agent SDK runs the agent loop on the builder's own host. Managed Agents is a hosted harness that tags every tool event with the permission it received and a reason code, and creates an immutable version for every memory write ([memory docs](https://platform.claude.com/docs/en/managed-agents/memory)). Its "dreaming" step consolidates memory into a new store and leaves the input untouched, so the owner can review the result. Every hosted layer keeps data at Anthropic, including Managed Agents with self-hosted sandboxes.

## Open-source agents

All 6 open-source agents document security controls that their defaults leave off:

| Project | Insecure default |
| --- | --- |
| OpenClaw | Sandboxing is off ([docs](https://docs.openclaw.ai/gateway/sandboxing)) |
| Hermes Agent | Shell commands run on the host, and a model judges approvals |
| NanoClaw | Egress lockdown is off ([`src/config.ts`](https://github.com/nanocoai/nanoclaw/blob/66f0823/src/config.ts#L106)) |
| IronClaw | Global auto-approve is on ([`auto_approve.rs`](https://github.com/nearai/ironclaw/blob/b0b999d/crates/kernel/ironclaw_approvals/src/auto_approve.rs#L43)) |
| ZeroClaw | Release builds leave out Landlock and Bubblewrap and fall back to no sandbox |
| Letta Code | The default permission mode allows every tool |

All 3 of the security-first projects, NanoClaw, IronClaw, and ZeroClaw, shipped a bug that accepted an approval response without checking who sent it or through which channel. Together these two findings support a stance that nixie's principles only imply: isolation refuses to start rather than degrade, and an approval binds to the owner's identity on a channel.

The defaults are insecure for a reason. An owner adopts a personal agent to remove friction, and each of these controls adds some: a sandbox breaks tools that expect the host, an egress lockdown breaks the first unlisted website, and an approval prompt interrupts the owner. A project that ships the controls on loses users to one that ships them off. nixie's controls therefore stay on and are each designed for the owner's experience first, so that the secure path is also the path with the least friction.

Each project still holds one or two strong mechanisms:

- **OpenClaw** binds each approval to the exact request, working directory, and executable hash, and never treats a free-text "yes" as consent. Its memory index stores where each entry came from, in columns the model cannot write. A destination-bound proxy swaps secrets in on the way out ([memory provenance](https://docs.openclaw.ai/concepts/memory-provenance), [exec approvals](https://docs.openclaw.ai/tools/exec-approvals)). Its record is weak: the audit ledger keeps metadata only, for 30 days. Its 722 published security advisories and a skill registry that served malware show the cost of in-process plugins and an open registry.
- **Hermes Agent** writes every change to a skill into an append-only ledger with the actor and before-and-after hashes, and rolls back any single entry. It records a delegated task whose process died as `unknown`, because it cannot prove whether the side effects happened. In its security policy, Nous Research treats isolation at the operating-system level as the only real boundary ([SECURITY.md](https://github.com/NousResearch/hermes-agent/blob/baef00bf4c6d9f009f19a7ecb3251849f4f7d54c/SECURITY.md)).
- **IronClaw** has the most complete design. Each tool's manifest declares its effects. A hard floor of financial, approval-changing, and budget-changing effects always asks, whatever mode is set. Its audit envelope records each action before, after, on denial, and at each approval stage, and production refuses an in-memory audit store ([`audit.rs`](https://github.com/nearai/ironclaw/blob/b0b999d/crates/contracts/ironclaw_host_api/src/audit.rs#L26)).
- **NanoClaw** runs the Claude Agent SDK in a container per session and refuses to start without a credential gateway, which injects real secrets by host and path ([docs](https://github.com/nanocoai/nanoclaw/tree/66f0823/docs)).
- **Letta Code** keeps memory as a git repository of markdown files, where every edit is a commit and a pre-commit hook enforces size limits and read-only files ([MemFS](https://docs.letta.com/letta-code/memfs)). Consolidation runs on a branch and merges back after an agent review.

## Recurring architecture models

The published writing and the code converge on 5 models. The table scores each one against nixie's principles.

| Model | Strongest source | Fits | Breaks |
| --- | --- | --- | --- |
| Session log, stateless harness, lazy sandbox | [Anthropic, "Scaling Managed Agents"](https://anthropic.com/engineering/managed-agents) | Nothing hidden; resumable execution; credentials stay out of the sandbox | Nothing, when self-hosted |
| Gateway with a container per session and a credential-injecting proxy | NanoClaw, OpenClaw, IronClaw | Untrusted content cannot reach out alone; brokered credentials | Owner data stays home, when the gateway runs in-process plugins |
| Out-of-band reference monitor keyed on provenance | [CaMeL](https://arxiv.org/abs/2503.18813), [FIDES](https://arxiv.org/abs/2505.23643) | Policy is deterministic and outside the runtime | Usefulness, unless policies stay cheap to write |
| Event-sourced durable execution | Temporal, Restate, DBOS | Resumable execution with actions safe to repeat | Nothing |
| In-band classifier gate | [Claude Code auto mode](https://anthropic.com/engineering/claude-code-auto-mode) | Owner friction | Policy is deterministic; a 17% miss rate on overeager actions rules it out of the catastrophic gate |

The evidence on prompt injection favours the out-of-band models. Adaptive attacks broke 12 published in-model defences at success rates above 90% ([Nasr, Carlini et al.](https://arxiv.org/abs/2510.09023)). Structural rules hold better because they do not depend on the model: a task holds at most two of untrusted input, sensitive access, and outbound action ([Meta, "Agents Rule of Two"](https://ai.meta.com/blog/practical-ai-agent-security/)), and credentials never enter the sandbox. A model classifier can add a deny on top of these rules, never an allow. Memory poisoning gets past every injection defence tested so far ([Dash et al.](https://arxiv.org/abs/2606.04329)), so a memory write is a privileged action.

The model that fits nixie combines 4 of them. A session log sits under a stateless harness and a lazy sandbox. Credentials are injected at egress by a host-side proxy. Policy runs as an out-of-band monitor at the tool boundary, keyed on where content came from. Memory is a versioned repository of markdown with provenance the model cannot write. No surveyed project combines all 4.

## Frameworks as a skeleton

None of the 3 frameworks works as a skeleton, because each one owns the agent loop and keeps policy inside it.

- **eve** puts approval in a code callback per tool, and its hooks cannot block an action. It records no rule against a decision. Its self-hosted path has an open bug that never resumes a turn killed mid-step ([vercel/eve#535](https://github.com/vercel/eve/issues/535)), and another that widens a deny-all network policy ([vercel/eve#3506](https://github.com/vercel/eve/issues/3506)). It does not support Bun. It published 228 releases between 9 June and 5 October 2026. Its contracts are worth copying: the steer and queue modes for new input, approvals as durable request and resolution events, the memory provider, and the sandbox provider, which a Firecracker service could implement.
- **Mastra** deletes approval snapshots after each run, sends telemetry to PostHog by default, and lost its entire npm scope to a supply-chain attack on 16 June 2026 ([mastra-ai/mastra#18061](https://github.com/mastra-ai/mastra/issues/18061)). Its channel layer, Vercel's Chat SDK, is MIT-licensed and usable on its own.
- **The Claude Agent SDK** runs the strongest agent loop and permission pipeline in the survey, and is the right runtime behind nixie's adapter. It is a runtime, not a skeleton: the scheduler, channels, owner identity, approval records, long-term memory, the spending stop, and the decision record are all nixie's own code.

The SDK's [permission order](https://code.claude.com/docs/en/agent-sdk/permissions) sets how nixie's adapter enforces policy. The SDK checks hooks first, then deny rules, ask rules, the permission mode, allow rules, and finally the `canUseTool` callback. A `PreToolUse` hook deny holds even in `bypassPermissions` mode, while an allow rule or the mode approves a call before `canUseTool` runs. The SDK's built-in default mode can be `auto`, a model classifier, since version 0.3.286. A `PreToolUse` hook can defer a call so the process exits and resumes later, but only in a `-p` run and only when Claude makes a single tool call in the turn. When Claude makes several tool calls at once, Claude Code ignores the `defer` with a warning, and the call goes through the normal permission flow ([hooks](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later)). Claude Code mods give the adapter a stronger place to enforce policy than a `PreToolUse` hook. A mod is a plugin of JavaScript or TypeScript event handlers that runs inside Claude Code, and its hooks run in the Agent SDK too; only its drawing is missing there ([mods overview](https://code.claude.com/docs/en/plugins/mods/overview)). Three of its events fit nixie ([events](https://code.claude.com/docs/en/plugins/mods/events)):

- `tool.call` sees every tool call, including a subagent's and an MCP tool's, before the permission check. A handler can deny the call, rewrite its arguments, answer it without running it, or hold it while it awaits a decision.
- `tool.check` fires after the permission rules and settings hooks have decided, and returns the final `allow`, `ask`, or `deny`. It can override a `PreToolUse` hook from any settings file outside managed settings.
- `turn.step` sees each request to the model before it is sent, with token usage after, so it can stop a request when a budget runs out.

A mod's hook that throws or times out is skipped, so the call runs. A `.catch` handler on the registration makes that hook fail closed instead. A `.catch` handler does not cover the whole mod: when the module fails to load, or when it crashes the shared hooks worker, Claude Code unloads the mod and the session continues without it ([troubleshoot](https://code.claude.com/docs/en/plugins/mods/troubleshoot)). The adapter must therefore check that the policy mod loaded, and stop the session when the mod is absent or unloaded. Order matters: the first mod in the chain sees every event first, and only `PreToolUse` hooks from managed settings run ahead of it, so nixie loads its own mod and no other.

The SDK's `maxBudgetUsd` is a client-side estimate that excludes restored sessions, so it is not a hard stop. The SDK is proprietary: its licence reads "© Anthropic PBC. All rights reserved". Anthropic's [terms guidance](https://code.claude.com/docs/en/legal-and-compliance#can-customers-offer-claude-code-in-their-products) still permits a product to preinstall and run Claude Code, on 2 conditions: the binary stays unmodified, and each end user authenticates with their own key or plan. A nixie owner runs nixie with their own key, so both conditions fit nixie.

## Recommendation for 2.2

Build nixie's core from 3 parts: an event log, a policy decision point, and the record. Run the Claude Agent SDK behind the runtime adapter, with policy enforced by a nixie mod on `tool.call` and `tool.check` that fails closed, `permissionMode` and `settingSources` set explicitly, and telemetry off. Use imp as the sandbox and credential broker. Its egress policy can make "a task that reads untrusted content has no route out" a property of the network, which no surveyed project achieves by default. One exception remains: a host that a credential grant covers stays reachable under every policy, through the broker ([imp egress](https://github.com/zgeoff/imp/blob/main/docs/architecture/networking.md#egress)). A reader task must therefore get no grant that reaches outside the owner's own systems. Put the hard spending stop in a proxy in front of the model, not in the SDK.

This sharpens the questions for track 2.2:

- How does the nixie mod reach the policy decision point, and how does it stay within a hook's time limit when the owner takes minutes to answer?
- How does an approval survive a restart, given that `defer` works only when Claude makes a single tool call in the turn?
- Does the event log come from the SDK's `SessionStore`, from nixie's own log, or from both?
- Which engine gives step-level resumption with idempotency keys on every outside action?
- How does a message from the owner reach a running task, given the SDK's streaming-input priorities `now`, `next`, and `later`?

## Corrections to the first survey

The first survey pass, before phase 1, got 4 facts wrong:

- The "512 findings" against OpenClaw came from an automated scanner run posted as [openclaw/openclaw#1796](https://github.com/openclaw/openclaw/issues/1796), not from an audit by Kaspersky or anyone else.
- Gemini Spark launched in May 2026, not August.
- Hermes Agent is not OpenClaw's successor. It is an independent project by Nous Research.
- The plan to spike eve as a skeleton no longer holds, for the reasons under [Frameworks as a skeleton](#frameworks-as-a-skeleton).

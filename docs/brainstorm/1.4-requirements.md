# Requirements

Each requirement traces to a job kind in [Jobs](./1.2-jobs.md), a principle in [Principles](./1.3-principles.md), or the statement in [Why nixie](./1.1-why.md). A requirement belongs to one of two classes:

- **Foundation**: the architecture accounts for it from the start, because adding it later means a redesign.
- **Extension**: it plugs into an interface that the foundation defines, so it can arrive at any point.

The class sets how the design treats a requirement, not when it ships. Delivery is piecemeal across both classes.

## Conversation and channels

| Requirement | Source | Class |
| --- | --- | --- |
| Two-way, asynchronous conversation: either side sends at any time, and a message from the owner reaches tasks that are already running | Why nixie | Foundation |
| Voice in both directions, with interruption | Why nixie | Foundation |
| One conversation that continues across channels, such as a chat app, voice, and a terminal | Why nixie | Foundation |
| nixie starts a conversation and pushes to the owner | Briefings, reminders, background work | Foundation |

Realtime voice models come from model providers. nixie integrates one through an adapter and does not build its own.

## Policy and trust

| Requirement | Source | Class |
| --- | --- | --- |
| A policy engine outside the runtime: deterministic, with a risk stance per context and an owner override | The owner has root; policy is deterministic; risk stance is set per context | Foundation |
| Approvals stored as records, scoped to an action and a target, with an expiry | The owner has root | Foundation |
| A record of every decision and action, with raw export | Nothing is hidden | Foundation |
| Task isolation: a task that reads untrusted content has no route out | Untrusted content cannot reach out alone | Foundation |

## Extension points

The foundation defines each interface. Implementations arrive as extensions.

| Requirement | Source | First implementation |
| --- | --- | --- |
| Agent runtime adapters | Any model, through adapters | Claude Agent SDK |
| Connectors to the owner's services and tools, including other agents | Upkeep of an owner's service; steering other agents | Open |
| Acting in the outside world, behind the catastrophic-outcome gate | Acting in the outside world | Open |
| Local models for private data | Work on private data | Open |

## Open questions

- Model Context Protocol (MCP) covers tools that an agent calls. Channels, event triggers, and credential brokering need interfaces beyond it. Which interfaces does nixie define, and which does it take from MCP?
- Which requirements are missing? A survey of existing assistants and frameworks feeds this list.

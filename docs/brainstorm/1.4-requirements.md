# Requirements

Each requirement traces to a job kind in [Jobs](./1.2-jobs.md), a principle in
[Principles](./1.3-principles.md), the statement in [Why nixie](./1.1-why.md), or a gap that a
survey of existing assistants and frameworks found. A requirement sits in one of three tiers, which
set the order of delivery:

| Tier | Meaning                                                                              |
| ---- | ------------------------------------------------------------------------------------ |
| 1    | nixie is unusable without it. The owner starts using nixie once tier 1 lands.        |
| 2    | nixie is effective across tasks with it. Each item is a focused unlock of behaviour. |
| 3    | A pure extension.                                                                    |

A ★ marks a requirement that the architecture designs for from the start, whatever its tier, because
adding it later means a redesign.

nixie integrates a realtime voice model through an adapter and does not build one. nixie owns the
voice session itself: it reconnects when a provider session ends, keeps a transcript of what the
owner heard, and brings in results without interrupting.

## Open questions

- Which parts form the core, and which sit behind an interface? Treat almost every capability as an
  adapter behind a contract, so tier 1 ships crude adapters and later work replaces them. The event
  and conversation loop, the policy decision point, and the record stay in the core, because policy
  has to live outside any runtime.
- Model Context Protocol (MCP) covers tools that an agent calls. Channels, event triggers, and
  credential brokering need interfaces beyond it. Which interfaces does nixie define, and which does
  it take from MCP?
